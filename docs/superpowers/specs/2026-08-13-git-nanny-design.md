# Нянька для веток (git-nanny) — дизайн

## Что это

Терминальная утилита для уборки локальных веток. Показывает ветки, отсортированные по «мёртвости» (вмёржена, удалена на remote, давно не трогали), даёт отметить их пачкой и снести. Отдельный режим — «снести всё, кроме основной».

Бинарь называется `git-nanny`, поэтому git подхватывает его как подкоманду: работает и `git-nanny`, и `git nanny`. Никаких алиасов настраивать не нужно.

## Зачем нянька, а не однострочник

`git branch --merged | grep -v main | xargs git branch -d` покрывает треть задачи и молча ломается на остальных двух:

- ветка, влитая **сквошем** (обычный режим GitHub/GitLab), в `--merged` не попадает — а именно таких больше всего;
- ветка, чей upstream удалён после мержа PR, тоже не попадает;
- при этом однострочник ничего не сообщает про ветки с несохранённой работой — а именно их удаление и страшно.

Нянька закрывает всё три случая и, главное, ведёт журнал удалений, из которого любую ветку можно вернуть одной командой.

## Критерии успеха

- Уборка кладбища веток в чужом репозитории занимает меньше минуты и не требует читать документацию.
- Ни одного случая потери работы: ветка с уникальными неотправленными коммитами не удаляется без явного подтверждения, и любое удаление обратимо.
- Ноль настройки: запустил в репозитории — работает.

## Модель безопасности

Удаление веток необратимо на вид, поэтому вся конструкция крутится вокруг этого.

**Никогда не удаляются** (даже с `--all-but-default`, даже с `--force`):

- текущая ветка;
- основная ветка репозитория;
- ветка, занятая другим worktree;
- ветки, попавшие под защиту: флаг `--protect <glob>` (можно несколько) или git-config `nanny.protect` (несколько значений). Конфиг берётся из самого git — своего формата настроек не заводим.

**Журнал удалений.** Перед каждым удалением в `~/.local/state/git-nanny/deleted.jsonl` пишется строка: путь репозитория, имя ветки, SHA, категория, время. `git nanny restore` показывает последние удаления по текущему репозиторию и возвращает выбранные (`git branch <name> <sha>`). Объект коммита живёт до сборки мусора (по умолчанию не меньше двух недель), так что окно восстановления реальное.

**Подтверждения.** В интерактивном режиме — экран подтверждения со списком. В неинтерактивном удаление не происходит без `--yes`; без него печатается план и код возврата 0. `--all-but-default` дополнительно требует `--yes` — случайный запуск ничего не сносит.

## Категории «мёртвости»

Каждой ветке присваивается ровно одна категория; она же определяет порядок и предвыбор.

| Категория | Что значит | Как определяется | Предвыбрана |
|---|---|---|---|
| `merged` | влита в основную | `merge-base --is-ancestor` **или** сквош-детект | да |
| `gone` | upstream удалён на remote | `%(upstream:track)` содержит `gone` | да |
| `stale` | давно не трогали, upstream нет | последний коммит старше N дней (по умолчанию 90) | нет |
| `active` | всё остальное | — | нет |

Сортировка: сначала категория в порядке таблицы, внутри категории — по дате последнего коммита от старых к новым.

**Сквош-детект** — то, ради чего утилита существует. Для ветки `B` берём `base = merge-base(default, B)`, создаём временный коммит с деревом `B` поверх `base` (`git commit-tree`) и спрашиваем `git cherry default <tmp>`: ответ, начинающийся с `-`, означает, что эквивалентный патч в основной ветке уже есть. Приём известный (так работает `git-delete-squashed`), временный коммит остаётся висячим объектом и убирается штатным `gc`.

## Что показывается по каждой ветке

`имя · последний коммит (относительно) · ahead/behind · upstream · причина категории`

Пример строки: `feature/pdf-export · 94 дня назад · +0/−128 · upstream удалён · вмёржена сквошем`.

Числа `ahead` берутся относительно основной ветки, а не upstream: вопрос, на который отвечает нянька, — «потеряю ли я работу», а не «синхронизирован ли я с сервером».

## Режимы запуска

```
git nanny                      # интерактивный список
git nanny --merged --yes       # снести только вмёрженные, без вопросов
git nanny --all-but-default --yes   # снести всё, кроме основной (и защищённых)
git nanny --stale-days 30      # порог «давно не трогали»
git nanny --protect 'release/*' --protect wip
git nanny --dry-run            # только показать план
git nanny restore              # вернуть удалённое
```

Ветки с уникальными коммитами относительно основной удаляются только с `--force` (или явной отметкой в интерактивном режиме — там пользователь видит, что делает). Без `--force` они пропускаются с пометкой «есть уникальные коммиты».

## Архитектура

```
cmd/git-nanny/main.go     — разбор флагов, выбор режима, коды возврата
internal/gitrepo/         — тонкая обёртка над git (exec): список веток с метаданными,
                            основная ветка, worktree, удаление, сквош-детект
internal/classify/        — чистые функции: категория, сортировка, фильтры защиты
internal/journal/         — запись удалений и восстановление
internal/ui/              — интерактивный список на Bubble Tea
```

Граница проведена так, чтобы всё, что можно проверить без git, проверялось без git: `classify` получает готовые структуры `Branch` и не знает, откуда они. Слой `gitrepo` тестируется на настоящих временных репозиториях — это единственный честный способ проверить сквош-детект и `gone`.

Git вызывается через `exec` фарфором и плумбингом; библиотека go-git не берётся: она тянет большую зависимость ради того, что уже установлено на машине.

## Зависимости

Bubble Tea, Bubbles и Lipgloss — только для интерактивного экрана. Вся логика и неинтерактивные режимы работают без них, поэтому утилита остаётся полезной, даже если TUI когда-нибудь выкинуть.

## Тесты

- `classify`: категории на всех границах (ровно N дней, ahead=0/1, защита по glob), порядок сортировки, стабильность при равных датах.
- `gitrepo`: временный репозиторий в `t.TempDir()`, в нём — обычный мерж, сквош-мерж, ветка с удалённым upstream (через второй локальный репозиторий как remote), ветка с уникальными коммитами. Проверяется, что каждая распознаётся правильно.
- `journal`: запись и восстановление, включая случай, когда файла ещё нет.
- Защита: тест, что текущая, основная и worktree-ветки не попадают в план удаления ни в одном режиме.

## Вне рамок

- Удаление веток на remote: чужая территория, ломает работу коллег.
- Разбор PR через GitHub/GitLab API: требует токенов, привязывает к хостингу.
- Слияние, переключение, rebase — нянька только убирает.
- Windows: цели — macOS и Linux (на Windows соберётся, но проверяться не будет).
